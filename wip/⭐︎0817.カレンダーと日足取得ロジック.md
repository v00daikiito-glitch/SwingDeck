## 1. 方針転換: カレンダーを持つ

### 以前の方針（廃止する）

祝日カレンダーは自前で持たない。取得先に聞いて、返ってきた日だけを信じる。祝日で何も返らなければ何も保存しない。プロトタイプも土日以外の祝日は無視していた。

### 変える理由

確定日足の更新は、次が必要になる。

- 手元の一番新しい日足は、どの日付か  
- 「いま持っているべき、もう閉まっている最新の営業日」はどの日付か  
- 古ければ、足りない分を取りに行く  

カレンダーが無いと、次の区別がつかない。

- 休場だから無い  
- 通信に失敗したから無い  
- 途中の営業日の足が欠けている  

欠けると、その銘柄だけ日足の並びが詰まり、チャートがずれる。休場日を休場と分からないと、足が無いのは祝日のせいなのに「まだ最新に追いついていない」と判定し、同じ日を何度も取りに行く。以前カレンダーを避けた主因は再配布だった。白寄りと分かったので、カレンダーを持つこととする。



### カレンダーの役割と、値段の正本

- 値段の正本は取得先。返してきた足だけ保存する。カレンダーが休みと書いていても、取得先が足を出せば保存する。カレンダーで間引いて捨てない  
- カレンダーは「取りに行く／行かない」「欠けと休場を分ける」ための目安。値段の正本にはしない  

カレンダーが外れる日はある。

**営業日と書いてあるのに休場（国葬、台風、急な祝日）**  
取りに行って空が返る。こういう日は稀なので、カレンダーが実態とずれていても許容する。ただし、同じ日を無限に取りに行かない（§5 の fetch 間隔、§8 の確認済みの空。後述）。

**休みと書いてあるのに開いている（カレンダー遅れ、誤記）**  
より性質が悪い。カレンダーを信じて取りに行かないと、その日の足が永久に欠ける。

これから先（最近の分）の防ぎ方: 追いつき取得は「予想の1日だけ」ではなく「手元の最後の日から先」を期間でまとめて聞く。この区間の中なら、カレンダーが休みと書いてある日も、取得先が足を出せば返ってくる。返ってきたら保存する。

例: カレンダーは月曜休み。実際は開いていた。手元の最後は金曜。火曜の大引け後、金曜から先を取る。その中に月曜が入る。取得先が月曜を出せば保存される。

昔の分（一番新しい足より前で、カレンダーは休み、取得先には足がある、手元には無い）: カレンダーと日足の diff では見つからない。diff が見るのは「カレンダーは営業日なのに `daily_bars` に無い」だけ。逆は条件に入らない。

何年も前の日に、あとから足が生える前提は置かない。初めてその銘柄の履歴を取るときに、取得先が持っていた日は入っている。2ヶ月前の空白が、1ヶ月以上経ってから突然埋まる、は想定しない。代わりに、取得先があとから直す・足すのはおおよそ1ヶ月以内、という前提で設計する。カレンダー diff で拾えない古い日も、1ヶ月経ってから取得先にもう一度聞く（おさらい。印で管理。§10）。

### チャートの欠け

週足・月足は、日が1日欠けても「穴の足」としては見えにくい（1本にまとまる）。中身の高安・出来高は少し狂い得るが、見た目の穴にはならない。問題は日足チャート。

表示は、証券アプリと同じく**営業日の足だけ右に詰める**。欠けた営業日を空白で1本飛ばさない。空白は休場に見えて分かりにくい。正しい対処は、表示で穴を空けることではなく、検知して取り直して埋めること。埋まるまでは詰めたまま出す。

## 2. カレンダーの中身と自動差し替え

### テーブル案 `market_calendar`

「営業日だけを並べる」のではない。対象期間の**暦日を全部**入れ、営業日フラグを付ける。営業日だけだと、途中欠損と休場の区別がつかない。

| 列 | 意味 |
| --- | --- |
| `country` | `JP` / `US` |
| `trade_date` | `YYYY-MM-DD`。対象期間の全日 |
| `is_trading_day` | 1=営業日、0=休場 |
| `is_half_day` | 1=早引け、0=通常（オプション。詳細は未設計。今は枠だけ） |
| `source` | 例: `pandas_market_calendars` |
| 主キー | `(country, trade_date)` |

ファイル全体に `version`（または作った日時 `generated_at`）を付ける。

生成は Python の `pandas_market_calendars`（MIT）。JPX と NYSE。過去〜未来の長期分。出力は上記の形の JSON（または同等）。人が毎年思い出す作業にはしない。スクリプトで生成する。

行数は少ない（例: 40年×2カ国でも数万行）。端末に置いても軽い。

### 自動差し替え（人手なし。後回しにしない）

年1回、人が手で差し替える前提にはしない。忘れる前提で、人が介在しない道を今の設計に含める。

サーバーがまだ無くても、アプリ側の更新の流れは後から変えない。最初は、カレンダーファイルをアプリに入れて配る（サーバーは使わない）。置き場がサーバーになっても、version の比較と差し替えだけで済むようにする。
いつもの日足取得・判定で使うのは、常に手元のカレンダー。サーバー（または配信 URL）に行くのは、カレンダー本体の更新確認・差し替えのときだけ。



1. カレンダーに `version`（または作った日時）を付ける  
2. 起動時（または定期）に、手元の `version` と配信側の `version` を比べる（サーバーが無い段階ではこの確認はスキップしてよい）  
3. 配信側の方が新しければ、手元のファイルを差し替える  
4. 失敗・オフラインならエラーにせず、手元のまま動かす  

生成バッチをサーバーで定期実行し、静的ファイルとして公開する形も、今の設計に含めておく。サーバーを置いたときにそのまま使える。

端末に `pandas` や `pandas_market_calendars` は載せない。生成はサーバー（またはビルド時）。端末は出来上がった表を持つだけ。

## 3. 確定日足の取得で使う記録（①②③。おさらいの印は 2/2）


### ① 手元の一番新しい日足の日付

`daily_bars` に、その銘柄の足が何本入っているかは銘柄ごとに違う。そのうち **いちばん新しい `trade_date`** が ①。

追いつきの始点は **①**。「前回アプリを開いた日」でも、「今日の日付」でもない。

例（どちらも12月10日にアプリを開く）:

- 大引け前に開く … 10日分はまだ確定していない。取れたのは9日まで → ①は12月9日。
- 大引け後（16:00以降）に開いて、その回で10日分まで取れた → ①は12月10日。

①が進むのは、アプリを開いたからではなく、取りに行って足が保存されたとき。いつ開くかと、①が何日かは一致しない。

### ② 取得先が返事した時刻

取得先がエラーなく答えたときだけ記録される。中身が0件でもよい。通信エラー・時間切れでは記録されない。

使い道は連打防止ではない。あとから「この日は足が無いと、取得先が空で答えた」とみなすとき用。
置き場所は、下記の `symbol_fetch_status` を参照。

### ③ 取りに行った時刻（結果を問わない）

`update_daily_bars`（`catch_up_daily_bars` / `review_daily_bars` を含む）が fetch に行った時刻。足が来た／0件／通信エラー、のどれでも残す。アプリを閉じても残る。

使い道: **`update_daily_bars` を、同じ銘柄について1時間に1回まで**に制限する（§3.5）。結果を問わず、取りに行ったら更新する。

`update_snapshot` の間隔（30分）は、`latest_snapshots.updated_at` を見る（`symbol_fetch_status` には載せない）。

### `symbol_fetch_status`（銘柄1行）

表名（仮）は `symbol_fetch_status`。銘柄1つにつき1行。

| カラム | 中身 |
| --- | --- |
| `symbol_id` | 銘柄。主キー |
| `last_answered_at` | ② 取得先が返事した時刻 |
| `last_attempted_at` | ③ `update_daily_bars` が取りに行った時刻 |
| `review_complete_date` | おさらいの印（その日以前は、1ヶ月経ったあとの取り直し済み） |
| `daily_bar_locked_until` | `update_daily_bars` をスキップする期限。確定足取得成功後、翌営業日の 16:00 頃まで（§3.5） |
| `snapshot_locked_until` | `update_snapshot` をスキップする期限。確定足取得成功後、翌営業日の寄付（9:00）まで（§3.5） |

`daily_bars` には足さない。


## 3.5 `daily_bars` と `latest_snapshots`（確定日足と snapshot）

配信元（Yahoo 等）では、**気配・現在値** と **日足履歴** は別の取り方になる。SwingDeck も保存先を分ける。

| | 確定日足 | snapshot（その日の仮足） |
| --- | --- | --- |
| 保存先 | `daily_bars` | `latest_snapshots` |
| Adapter | `fetch_daily_bars` | `fetch_snapshot` |
| DailyBarService | `update_daily_bars` | `update_snapshot` |
| 中身 | 大引け後に確定した営業日の OHLCV。不変 | その取引セッションの進行中 OHLCV。上書き更新 |
| ユーザーが欲しいもの | 新しい**確定日足** | 場中チャートの**いまの足**、インディケータ・フィルター計算の元 |

15:30 頃に証券アプリで見える終値は、配信元の quote 系（≒ snapshot 側）であることが多い。`fetch_daily_bars` で今日の1本が返るタイミングは、それより遅いことがある。詳細は §4・§5。

### きっかけと呼び出し順

価格更新ボタン／アプリ起動／プレイリスト表示／デッキ表示など、ユーザ操作のたびに、監視銘柄について **次の順** で走らせる（`01_Data_Layer.md` と同じ）。

1. `update_daily_bars_for_watchlist` … 銘柄ごとに `update_daily_bars`  
2. `update_snapshots_for_watchlist` … 銘柄ごとに `update_snapshot`  

個別チャート表示時は、対象1銘柄だけ `update_daily_bars` → `update_snapshot` の順。

新しいサービスは作らない。DailyBarService の既存メソッド名を使う。

### `update_daily_bars` の中身

`update_daily_bars(symbol_id)` は、次の2つを順に呼ぶ（詳細は §5・§10）。

1. `catch_up_daily_bars(symbol_id)` … **追いつき**（①から、持つべき確定営業日まで）  
2. `review_daily_bars(symbol_id)` … **おさらい**（印の管理で、1ヶ月経った古い日を再取得）。ユーザー向け機能ではなく、裏方のメンテ  

### 確定足が取れたあと（snapshot との関係）

ある銘柄で `catch_up_daily_bars` が成功し、その日の確定足（例: 12/10）が `daily_bars` に入ったら:

- その銘柄の `latest_snapshots` 行を**削除**する（同じ日付の仮足を残さない）  
- **`update_snapshot` は、次の取引セッションの寄付（東証 9:00）までスキップ**する（`snapshot_locked_until`。§3 の表）  
- **`update_daily_bars` は、翌営業日の確定日足が取れる時刻（東証 16:00 以降）までスキップ**する（`daily_bar_locked_until`。§3 の表）  

例: 12/10 17:00 に 12/10 の確定足が入った → snapshot 削除。`update_snapshot` は 12/11 9:00 までロック。`update_daily_bars` は 12/11 16:00 までロック。12/11 9:00 から `update_snapshot` が再開（12/11 の snapshot 用）。12/11 16:00 から `update_daily_bars` が再開（12/11 の確定足用）。

### fetch の間隔（銘柄ごと）

- `update_daily_bars` … **1時間に1回まで**（`last_attempted_at` を見る）  
- `update_snapshot` … **30分に1回まで**（`latest_snapshots.updated_at` を見る）  

スキップ判定があるので、ボタンを連打しても、上記より多く fetch しない。


## 4. 持つべき最新の確定営業日（追いつきの終点）

`catch_up_daily_bars` が「いま手元に **あるべき** 最新日足」を決めるときの **終点**。①（手元にある最新日足）とは **別の日付** として扱う。

**確定日足として扱える、いちばん新しい営業日** を指す。カレンダー上の「今日」とは限らない。

### ① との関係

| | ① | 本節の終点 |
| --- | --- | --- |
| 意味 | `daily_bars` に **実際にある** 最新の `trade_date`（銘柄ごと） | **持っているべき** 最新の確定営業日（市場単位で計算） |
| 使い道 | `catch_up_daily_bars` の **始点** | `catch_up_daily_bars` の **終点** |

`catch_up_daily_bars` は、①と本節の終点を比べる。**同じなら取りに行かない。** ①の方が古ければ、不足分を取りに行く。

例（12月10日）:

- 10:00 … 10日分はまだ確定していない。終点は12月9日。①も9日なら追いつき不要。  
- 17:00 … 10日分が確定したとみなせる。終点は12月10日。①が9日なら、10日分を取りに行く。

### snapshot との関係

15:30 頃に証券アプリで見える終値は、配信元の quote 系（≒ `fetch_snapshot`）であることが多い（§3.5）。本節の終点は **`fetch_daily_bars` で確定日足として扱える日** の話。同じ時刻ではない。

### 東証の時刻（他市場は同様の考え方で定数を持つ）

- **15:30** … 立会外を含め、終値が出揃う。  
- **16:00 以降** … `fetch_daily_bars` で「今日の確定足が載る」とみなしてよい **最初の時刻**（市場単位。銘柄ごとには判定しない）。  
- **16:00 より前**に全銘柄一括で取りに行かない。早すぎると、まだ空の銘柄が多く、無駄な fetch になる。  

ごく一部の銘柄だけ、日足履歴 API に載るのが遅いことがある。§5 の **1時間に1回** の再試行で、その夜のうちに拾う。

アプリを開く時刻を人ごとにずらすのは、取得先の負荷分散用（既存方針）で、上記の 16:00 待ちとは別。

## 5. `catch_up_daily_bars`（追いつき）

`update_daily_bars(symbol_id)` の最初に呼ぶ。銘柄ごと。ユーザーが欲しいのは **新しい確定日足** が主で、ここがその本体。

### スキップ（取りに行かない）

次のいずれかなら、`catch_up_daily_bars` は何もしない。

1. `daily_bar_locked_until` より前（§3.5。確定足取得成功後、翌営業日 16:00 頃まで）  
2. `last_attempted_at` から **1時間以内**（§3.5）  
3. ① と §4 の終点が **同じ**  

### 手順

1. 上のスキップを確認する  
2. ① を見る  
3. カレンダーと時刻から、§4 の **終点**（持つべき最新の確定営業日）を出す  
4. ① と終点が同じなら終了  
5. **始点**を決める  
   - 通常: ① の `trade_date` から（その日の upsert 可）  
   - ① が今日の30日前より古い: **印** から（`review_daily_bars` は別関数だが、①が古いときは `catch_up_daily_bars` 1本にまとめてよい。詳細 §10）  
6. **終点**まで `fetch_daily_bars` で期間取得する  
7. 取りに行ったら、結果に関わらず `last_attempted_at`（③）を更新する  
8. 取得先が返事したら（0件でも）②を更新する。通信エラーなら②は触らない  

### 成功したとき（その銘柄）

- 返ってきた足を `daily_bars` に upsert する  
- ① が進む  
- その日の確定足（例: 12/10）が入ったら、§3.5 どおり `latest_snapshots` を **削除** し、`snapshot_locked_until`（翌営業日 9:00）と `daily_bar_locked_until`（翌営業日 16:00 頃）をセットする  
- ① が今日の30日前より古かった場合は、印を今日の30日前に進める（§10）  

### 空と失敗の見分け

- 普通に返ってきたが、その日の足が0件 → **空**（国葬など）。②を更新する。`last_attempted_at` も更新する。  
- つながる前に落ちた、時間切れ、エラー番号 → **失敗**。②は触らない。`last_attempted_at` は更新する。  

「直近営業日の閉場以降に②があれば、もう確認したとみなして終了」という案は、**空の返事でその夜を打ち切ってしまう**ので採用しない。

通信エラーで②を進める案も不採用。失敗なのに「もう確認した」になり、次の大引けまで取り直さない。

### `review_daily_bars` との順番

同じ `update_daily_bars` のなかで、`catch_up_daily_bars` の **あと** に `review_daily_bars` を呼ぶ（§10）。おさらいはユーザー向け機能ではなく、裏方のメンテ。`daily_bar_locked_until` 中は、`catch_up_daily_bars` がスキップされれば `review_daily_bars` も実質走らない。

## 6. `update_snapshot`（snapshot 取得）

`update_daily_bars_for_watchlist` の **あと** に、`update_snapshots_for_watchlist` で銘柄ごとに呼ぶ（§3.5）。

### 用途

- 場中の日足チャートの **いまの足**  
- インディケータ・サブインディケータ・フィルターなど、**最新足を元にする計算**  

確定日足の追いつき（`catch_up_daily_bars`）とは別。混ぜない。

### スキップ（取りに行かない）

次のいずれかなら、`update_snapshot` は何もしない。

1. `snapshot_locked_until` より前（§3.5。確定足取得成功後、翌営業日 9:00 まで）  
2. `latest_snapshots.updated_at` から **30分以内**（§3.5）  

`catch_up_daily_bars` が成功して `daily_bars` にそのセッション日の足が入っている間は、`snapshot_locked_until` により snapshot は取らない。同じ日付の足が二重に存在しない（§3.5）。

### 手順

1. 上のスキップを確認する  
2. `fetch_snapshot` で取得する  
3. `latest_snapshots` に upsert する（`updated_at` を更新）  

### 再試行

`update_daily_bars` は **1時間に1回**、`update_snapshot` は **30分に1回**。ボタンや起動のたびに処理は **呼ばれる** が、上記を満たさない銘柄はスキップする。

16:00 に `catch_up_daily_bars` が空振りしても、17:00・18:00 … と **1時間おき** に再試行できる（`daily_bar_locked_until` に達する前）。15分ごとの別枠再試行は採用しない。遅い銘柄も、1時間以内の次の試行で拾う。

17:00 以降も、ロック前かつ1時間経過していれば試行してよい。取れなければ ① は古いまま。翌営業日 9:00 から `update_snapshot` が動き、16:00 から再び `catch_up_daily_bars` が動く。

## 7. 翌日以降: `catch_up_daily_bars` と、途中の穴は別処理

月曜の足が、その夜の `catch_up_daily_bars` では来なかったとする。手元の①は、まだ金曜のまま。

**火曜 16:00 以降（`catch_up_daily_bars` が動く）:**

- ①はまだ金曜  
- §4 の終点（持つべき最新の確定営業日）は火曜  
- ①と終点が違う → `catch_up_daily_bars`。「金曜から先」を期間取得する  

ここで火曜の足が来る。月曜も来れば終わり。月曜だけ来なければ、その時点で①は火曜になり、月曜が途中の穴になる。

**そのあと（次の価格更新、または同じ回の見比べ）:**

- ①と§4 の終点が同じ（火曜＝揃っている）  
- 月曜だけ無い → `catch_up_daily_bars` は走らない  
- ここで初めて、カレンダー diff: 手元のカレンダーと手元の日足を見比べ、欠けた日だけ取りに行く  

「翌日の大引け後は diff だけ」は、火曜の足が既に手元にあるあと。火曜の足をまだ持っていない時点では、まだ `catch_up_daily_bars`。火曜の足をまだ持っていないのに diff だけ、と飛ばすのは誤り。

## 8. 途中の穴の見比べ（カレンダー diff）

`catch_up_daily_bars` は「①が §4 の終点まで来ているか」だけ見る。最後が揃っていても、先週の営業日が1日欠けている、は見逃す。途中の穴は別確認。

これは `review_daily_bars`（おさらい）とは別物。名前を混ぜない。

カレンダー diff は2段に分ける。

1. 手元のカレンダーと手元の日足を見比べる（通信しない）  
2. 欠けていた日のうち、「まだ空と確認していない日」だけ、取りに行く  

見比べの条件は「カレンダーは営業日（`is_trading_day = 1`）なのに、`daily_bars` に無い」。休みと書いてある日は、この diff の対象外。1/2 に書いた「カレンダーは休み、取得先には足がある、手元には無い」パターンは、ここでは拾わない（`review_daily_bars` 側の話）。

1は端末の中の照合。監視100銘柄・10年でも体感は一瞬のことが多い。価格更新のたびに走らせてよい。重いのは2の、Yahoo 等へ取りに行くとき。

全期間をYahooから取り直す、はしない。欠けが無ければ通信はゼロ。

国葬のように、カレンダーだけ営業日で、何度取っても空、という日は、毎日・毎週取りに行かない。取りに行って0件で返事が来たら、その銘柄のその日は「足は無いと確認済み」と残す。次の見比べでは穴に数えない。fetch はその日について原則1回で終わり。通信エラーの回は「確認済みの空」にしない（また取りに行けるようにする）。

確認済みの空の置き場所は、②（銘柄1つの時刻）とは別。`(銘柄, 日付)` ごと。

カレンダー差し替え後に、営業日フラグが変わった日は、確認済みを見直す必要があるかもしれない。そこは設計書に落とすとき、一言決める。

週1で空と分かっている日を取りに行く案は不採用。空と分かったあとは、1日1回も週1も不要。

## 9. 国葬と遅れの具体例（同じ流れで両方扱う）

その場では区別できない。空でも、§5 のとおり **1時間に1回** `catch_up_daily_bars` を試せる（`daily_bar_locked_until` 前）。

**遅れ（本当は営業日で、取得先が遅い）:**  
16:00 空 → 17:00 以降の試行で足が来る → ①が進む → 終わり。

**国葬（カレンダーは営業日、実際は休場）:**  
16:00 以降も空振り。1時間おきに試しても空。火曜 16:00 以降の `catch_up_daily_bars` で火曜の足が来る。月曜は途中の穴。カレンダー diff で月曜を1回取りに行き、空なら確認済みの空。以後取りに行かない。

「次の確定営業日の足まで来たら確認済みの空にする」の意味は、上の国葬の切り替えのこと。月曜の夜に来ず、火曜の足が取れたあと、月曜は「最新に追いついていない」ではなく「途中の1日が欠けている」になる。欠けを1回取りに行き、来れば保存、来なければ確認済みの空。

## 10. `review_daily_bars`（おさらい）

`update_daily_bars` のなかで、`catch_up_daily_bars` の **あと** に呼ぶ（§5）。ユーザー向け機能ではなく、裏方のメンテ。取得先があとから古い日の足を直したり足したりしたとき、1ヶ月経過後にもう一度聞く。

### 前提

後から空白だったところに穴が埋まるのは、長くてもおおよそ1ヶ月以内、とする。2ヶ月前の日にいきなり足が生える前提は置かない。

初めてその銘柄の履歴を取るときに、取得先が持っていた日は入っている。何年も経って、カレンダーでは休みなのに実際には足があった日が、いきなり過去に入ってくる、は追わない。

印（`review_complete_date`）は、久しぶりに開いた人だけのものではない。毎日使う人向けの記録でもある。①と§4 の終点が同じで `catch_up_daily_bars` が走らない日でも、取得先があとから古い日の足を直したり足したりすることがある。印は「その古い日を、1ヶ月経ってからもう一度聞いたところまで」を残す。

月1回「直近30日を全部取り直す」をユーザーIDの30等分でずらす案は不採用。印（日付1欄）で足りる。

### 印（仮称: おさらい完了日）

銘柄ごとに日付を1欄持つ（§3 の `review_complete_date`）。別サービスは不要。`update_daily_bars` のときに見る。その銘柄の取得が失敗したら、その銘柄の印は進めない。

②や③（時刻）とは別で、日付。意味は「この日以前は、1ヶ月以上経ってから、取得先にもう一度聞いた」。

カレンダー diff（営業日なのに足が無い）とは別。名前を混ぜない。設計書に落とすとき、混同しない名前にする。

### ①と今日の30日前を比べる（`catch_up_daily_bars` と `review_daily_bars` の呼び方）

**①が今日の30日前より古い:**

- `review_daily_bars` は別に走らせない（`catch_up_daily_bars` 1本にまとめる）  
- `catch_up_daily_bars` の始点を **印** にする。終点は §4  
- 成功したら印を今日の30日前にする  

**①が今日の30日以内:**

- `catch_up_daily_bars`: 始点 ①、終点 §4  
- `review_daily_bars`: 印の次の日から今日の30日前まで（印がもう30日前なら何もしない）  
- `review_daily_bars` が成功したら印を今日の30日前にする  

### 印の進め方（具体例。この日付で固定）

**8月10日に、半年ぶり（①＝2月10日、印＝1月11日頃）に開く。**

- ①（2月10日）は、今日の30日前（7月10日）より古い → `review_daily_bars` は別に走らせない  
- `catch_up_daily_bars` 1回: 印（1月11日頃）から §4 の終点まで  
- 1月12日〜2月9日はDBにあっても、印より先でまだおさらい未完了の帯。印から取ればここも含まれる  
- 8月1日分を8月10日に「おさらい完了」にしてはいけない。まだ1ヶ月経っていない  
- 成功したら印を7月10日にする  

**4ヶ月空いて、12月10日に開く（①＝8月10日、印＝7月10日）。**

- ①（8月10日）は、今日の30日前（11月10日）より古い → `review_daily_bars` は別に走らせない  
- `catch_up_daily_bars` 1回: 印（7月10日）から §4 の終点（12月10日）まで  
- 7月11日〜8月9日も、印から取ればおさらい未完了分を含めて更新される  
- 成功したら印を11月10日にする  

**次に12月25日に開く（①＝12月10日、印＝11月10日）。**

- ①（12月10日）は、今日の30日前（11月25日）より後（＝今日の30日以内）  
- `review_daily_bars`: 印（11月10日）の次の日から11月25日まで。印を11月25日にする  
- `catch_up_daily_bars`: 12月10日から §4 の終点（12月25日）まで  
- 11月25日〜12月10日の間はもう持っている日。区間が空くので、1本にまとめない（§11）  
- 12月10日から25日の新しい分は、まだ1ヶ月経っていないので、おさらいの対象外  

### 取る範囲（`review_daily_bars`）

「印から今日まで」毎回取ると、毎日使う人は毎日、直近1ヶ月を全銘柄取り直す。重い。不採用。

取るのは **印の次の日から、今日の30日前（1ヶ月前）まで** だけ。今日の1ヶ月前より新しい日は、この処理では見に行かない。

毎日開くなら、1日分だけが新しく1ヶ月経つので、その1日だけ足す。12月25日、印が11月10日なら、11月11日から11月25日まで。

①が今日の30日前より古いとき（8月10日・12月10日の例）は、`review_daily_bars` は別に走らせず、`catch_up_daily_bars` 1本で印から取る。`review_daily_bars` 単独で「新しく1ヶ月経った区間」が長くなるのは、①が今日の30日以内で毎日使う場合の話。

8月10日時点で8月1日を `review_daily_bars` で見に行っても、まだ1ヶ月経っていないので意味が薄い。1ヶ月経った状態のときに見る。

## 11. `update_daily_bars` の中身（サービスは1つ）

サービスは `DailyBarService` ひとつ。新しいサービスは作らない。ユーザー操作のきっかけでは、監視銘柄について `update_daily_bars_for_watchlist` → `update_snapshots_for_watchlist` の順（§3.5）。

`update_daily_bars(symbol_id)` の中身は、次の2つを **順に** 呼ぶ（§5・§10）。

1. `catch_up_daily_bars(symbol_id)` … 追いつき（①から §4 の終点まで）  
2. `review_daily_bars(symbol_id)` … おさらい（印の管理。ユーザー向け機能ではない）

一つの関数に詰めない。`catch_up_daily_bars` と `review_daily_bars` を分ける理由は、始点・終点・印の進め方が違うから。呼び出し側（プレイリスト等）が二重になるのを防ぐため、外からは `update_daily_bars` だけ呼ぶ。

### ①と今日の30日前を比べる

10節（`review_daily_bars`・おさらい）の「①と今日の30日前を比べる」と同じ。具体例（8/10・12/10・12/25）も10節を見る。

### `catch_up_daily_bars`（追いつき）

- 始点: 通常は ①。①が今日の30日前より古いときは **印**  
- 終点: §4 の「持つべき最新の確定営業日」  
- 始点と終点が同じなら、何も取りに行かない  
- スキップ: `daily_bar_locked_until` 前、`last_attempted_at` から1時間以内（§5）  
- 取りに行ったら、結果に関わらず `last_attempted_at`（③）を更新する  
- 確定足が保存されたら、§3.5 どおり `latest_snapshots` を削除し、ロックをセットする  

15分ごとの別枠再試行は採用しない。空でも **1時間に1回** 試せる（§5）。

### `review_daily_bars`（おさらい）

- ①が今日の30日前より古いときは呼ばない（`catch_up_daily_bars` 1本にまとめる）  
- 始点: 印の次の日  
- 終点: 今日の30日前  
- 印が今日の30日前と同じ（またはそれ以降）なら、何も取りに行かない  
- 成功したら印を今日の30日前に進める。失敗したらその銘柄の印は進めない  
- スキップ判定は `catch_up_daily_bars` と同じ（`daily_bar_locked_until`、`last_attempted_at`）。`catch_up_daily_bars` がスキップされれば、実質 `review_daily_bars` も走らない  

### 通信を1本にまとめる／まとめない

「①が今日の30日前より古い」ときは、もともと1本（`catch_up_daily_bars` のみ）。

「①が今日の30日以内」のときだけ、`catch_up_daily_bars` と `review_daily_bars` の区間を見比べる。

区間が重なる／つながるとき:

- 古い方の始まりから §4 の終点までを1回で取ってよい  
- この判断は `update_daily_bars`（DailyBarService）の仕事  

区間が空くとき（12月25日など: おさらい 11月11日〜11月25日、追いつき 12月10日〜12月25日）:

- まとめない  
- 間（11月25日〜12月10日）はもう持っている日。1本にすると、持っている日まで取り直し、「毎回1ヶ月分」の無駄になる  
- 通信の回数より、取らなくてよい日を取り直す方が無駄  
- おさらいと追いつきは、別の期間のままそれぞれの関数が取る  

「重ならないときも11月10日から12月25日を1回」は不採用。

### 異常時（①と印の関係が壊れているとき）

追いつきだけ失敗して、印だけ進み、印の日付が①より新しくなっているときは、①から取る。§10 の具体例（8/10、12/10、12/25）とは別の話。

## 12. 既存の `DailyBarService` との接続（`01_Data_Layer.md` への落とし込み）

`01_Data_Layer.md` にある今のスキップは、おおむね次。

- `daily_bars` の最新 `trade_date`（①）と、「持つべき最新の確定営業日」（§4 の終点）を比べる  
- 揃っていれば `catch_up_daily_bars` は取りに行かない。足りなければ不足分だけ取る  
- きっかけはユーザ操作（起動、プレイリスト、デッキ、個別チャート、価格更新ボタン）  
- 定時の強制一括取得は作らない  
- 気配（snapshot）は `latest_snapshots.updated_at` で **30分に1回まで**  

今回決めたことは、次を足す（または置き換える）こと。

- 「持つべき最新の確定営業日」を **カレンダー** から出す（§4）  
- ①②③、`symbol_fetch_status` の列（§3 の表）  
- `update_daily_bars` = `catch_up_daily_bars` + `review_daily_bars`（§5・§10・§11）  
- `update_snapshot`（§6）。確定日足と snapshot は別 API・別保存先（§3.5）  
- 確定足取得成功後: `latest_snapshots` 削除、`snapshot_locked_until`（翌営業日 9:00）、`daily_bar_locked_until`（翌営業日 16:00 頃）（§3.5）  
- `update_daily_bars` … **1時間に1回**（`last_attempted_at`）。`update_snapshot` … **30分に1回**（`latest_snapshots.updated_at`）  
- 東証 **16:00 以降** から `fetch_daily_bars` で確定足を取りに行く（§4）。15分ごとの大引け後再試行グリッドは **採用しない**  
- 途中の穴: カレンダー diff（§8）、確認済みの空（§8）  
- おさらい: 印（`review_complete_date`）（§10）  
- 重なる区間だけ期間取得を1本にまとめる（§11）  

気配の30分区切りと、確定日足の1時間区切りは別。混ぜない。確定日足の③（`last_attempted_at`）は、開き直し連打の防止と、遅い銘柄の夜間再試行用。

失敗時の段階的リトライ（一括→失敗分だけ個別→もう一度）はプロトタイプの参考。今回の本文では、1時間に1回の再試行と、空／通信エラーの分けまで合意。段階の本数までは未固定。設計書に落とすとき、既存の「同じ時間枠では1回」と矛盾させない。

更新のきっかけは今どおりユーザ操作。おさらいも、起動やプレイリストを開いたときの `update_daily_bars_for_watchlist` に乗せる。おさらい専用の別バッチ・別サービスは作らない。ユーザーがアプリを開く日が人ごとに違うので、自然にずれる。同じ人の監視銘柄が同じ日にまとまっても、おさらいが「新しく1ヶ月経った分だけ」なら、毎日使う人は1日分程度。
