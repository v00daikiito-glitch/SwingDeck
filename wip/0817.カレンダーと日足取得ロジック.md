# SwingDeck 設計引き継ぎ（2026-08-17）カレンダーと確定日足の取得　1/2

このまとめは、設計書に落とすための材料です。**コード実装はまだしない。** ファイルの編集も、ユーザーが「このファイルを編集して」と書くまでしない。設計の一本の話が合意で固まってから、Before／After を出す。日本語は平易に。専門用語や①②③は、初出で意味を書く。たとえは具体的な日付で書く。凝縮した言い回しをしない。


## 0. このまとめの範囲

今回このスレで固めたこと（次スレの作業対象）:

1. 市場カレンダーを自前で持つ（以前の「持たない」方針からの転換）  
2. カレンダーの自動差し替え（人が毎年手作業しない。仕組みは今決める。最初の置き場はアプリ同梱でよい）  
3. カレンダーを使った**確定日足**（`daily_bars`）の取得判定。更新ボタンを押したとき／起動・プレイリスト表示などで `DailyBarService` が走る流れ  


## 1. 方針転換: カレンダーを持つ

### 以前の方針（廃止する）

祝日カレンダーは自前で持たない。取得先に聞いて、返ってきた日だけを信じる。祝日で何も返らなければ何も保存しない。プロトタイプも土日以外の祝日は無視していた。

### 変える理由

確定日足の更新は、次が必要になる。

- 手元の一番新しい日足は、どの日付か  
- 「いま持っているべき、もう閉まっている最新の営業日」はどの日付か  
- 古ければ、足りない分を取りに行く  

カレンダーが無いと、次の区別がつかない。

- 休場だから無い  
- 通信に失敗したから無い  
- 途中の営業日の足が欠けている  

欠けると、その銘柄だけ日足の並びが詰まり、チャートがずれる。休場日を休場と分からないと、足が無いのは祝日のせいなのに「まだ最新に追いついていない」と判定し、同じ日を何度も取りに行く。以前カレンダーを避けた主因は再配布だった。白寄りと分かったので、カレンダーを持つこととする。



### カレンダーの役割と、値段の正本

- 値段の正本は取得先。返してきた足だけ保存する。カレンダーが休みと書いていても、取得先が足を出せば保存する。カレンダーで間引いて捨てない  
- カレンダーは「取りに行く／行かない」「欠けと休場を分ける」ための目安。値段の正本にはしない  

カレンダーが外れる日はある。

**営業日と書いてあるのに休場（国葬、台風、急な祝日）**  
取りに行って空が返る。こういう日は稀なので、カレンダーが実態とずれていても許容する。ただし、同じ日を無限に取りに行かない（§6 の15分区切り、§8 の確認済みの空。後述）。

**休みと書いてあるのに開いている（カレンダー遅れ、誤記）**  
より性質が悪い。カレンダーを信じて取りに行かないと、その日の足が永久に欠ける。

これから先（最近の分）の防ぎ方: 追いつき取得は「予想の1日だけ」ではなく「手元の最後の日から先」を期間でまとめて聞く。この区間の中なら、カレンダーが休みと書いてある日も、取得先が足を出せば返ってくる。返ってきたら保存する。

例: カレンダーは月曜休み。実際は開いていた。手元の最後は金曜。火曜の大引け後、金曜から先を取る。その中に月曜が入る。取得先が月曜を出せば保存される。

昔の分（一番新しい足より前で、カレンダーは休み、取得先には足がある、手元には無い）: カレンダーと日足の diff では見つからない。diff が見るのは「カレンダーは営業日なのに `daily_bars` に無い」だけ。逆は条件に入らない。

何年も前の日に、あとから足が生える前提は置かない。初めてその銘柄の履歴を取るときに、取得先が持っていた日は入っている。2ヶ月前の空白が、1ヶ月以上経ってから突然埋まる、は想定しない。代わりに、取得先があとから直す・足すのはおおよそ1ヶ月以内、という前提で設計する。カレンダー diff で拾えない古い日も、1ヶ月経ってから取得先にもう一度聞く（おさらい。印で管理。§10）。

### チャートの欠け

週足・月足は、日が1日欠けても「穴の足」としては見えにくい（1本にまとまる）。中身の高安・出来高は少し狂い得るが、見た目の穴にはならない。問題は日足チャート。

表示は、証券アプリと同じく**営業日の足だけ右に詰める**。欠けた営業日を空白で1本飛ばさない。空白は休場に見えて分かりにくい。正しい対処は、表示で穴を空けることではなく、検知して取り直して埋めること。埋まるまでは詰めたまま出す。

## 2. カレンダーの中身と自動差し替え

### テーブル案 `market_calendar`

「営業日だけを並べる」のではない。対象期間の**暦日を全部**入れ、営業日フラグを付ける。営業日だけだと、途中欠損と休場の区別がつかない。

| 列 | 意味 |
| --- | --- |
| `country` | `JP` / `US` |
| `trade_date` | `YYYY-MM-DD`。対象期間の全日 |
| `is_trading_day` | 1=営業日、0=休場 |
| `is_half_day` | 1=早引け、0=通常（オプション。詳細は未設計。今は枠だけ） |
| `source` | 例: `pandas_market_calendars` |
| 主キー | `(country, trade_date)` |

ファイル全体に `version`（または作った日時 `generated_at`）を付ける。

生成は Python の `pandas_market_calendars`（MIT）。JPX と NYSE。過去〜未来の長期分。出力は上記の形の JSON（または同等）。人が毎年思い出す作業にはしない。スクリプトで生成する。

行数は少ない（例: 40年×2カ国でも数万行）。端末に置いても軽い。

### 自動差し替え（人手なし。後回しにしない）

年1回、人が手で差し替える前提にはしない。忘れる前提で、人が介在しない道を今の設計に含める。

サーバーがまだ無くても、アプリ側の更新の流れは後から変えない。最初は、カレンダーファイルをアプリに入れて配る（サーバーは使わない）。置き場がサーバーになっても、version の比較と差し替えだけで済むようにする。
いつもの日足取得・判定で使うのは、常に手元のカレンダー。サーバー（または配信 URL）に行くのは、カレンダー本体の更新確認・差し替えのときだけ。



1. カレンダーに `version`（または作った日時）を付ける  
2. 起動時（または定期）に、手元の `version` と配信側の `version` を比べる（サーバーが無い段階ではこの確認はスキップしてよい）  
3. 配信側の方が新しければ、手元のファイルを差し替える  
4. 失敗・オフラインならエラーにせず、手元のまま動かす  

生成バッチをサーバーで定期実行し、静的ファイルとして公開する形も、今の設計に含めておく。サーバーを置いたときにそのまま使える。

端末に `pandas` や `pandas_market_calendars` は載せない。生成はサーバー（またはビルド時）。端末は出来上がった表を持つだけ。

## 3. 確定日足の取得で使う記録（①②③。おさらいの印は 2/2）


### ① 手元の一番新しい日足の日付

`daily_bars` に、その銘柄の足が何本入っているかは銘柄ごとに違う。そのうち **いちばん新しい `trade_date`** が ①。

追いつきの始点は **①**。「前回アプリを開いた日」でも、「今日の日付」でもない。

例（どちらも12月10日にアプリを開く）:

- 大引け前に開く … 10日分はまだ確定していない。取れたのは9日まで → ①は12月9日。
- 大引け後（16:00以降）に開いて、その回で10日分まで取れた → ①は12月10日。

①が進むのは、アプリを開いたからではなく、取りに行って足が保存されたとき。いつ開くかと、①が何日かは一致しない。

### ② 取得先が返事した時刻

取得先がエラーなく答えたときだけ記録される。中身が0件でもよい。通信エラー・時間切れでは記録されない。

使い道は連打防止ではない。あとから「この日は足が無いと、取得先が空で答えた」とみなすとき用。
置き場所は、下記の `symbol_fetch_status` を参照。

### ③ 取りに行った時刻（結果を問わない）

足が来た／通信できたが0件／通信エラー、のどれでも残す。アプリを閉じても残る（起動中の記憶だけにしない）。連打による fetch 消費を防ぐケースに使用する。

例: fetch を15分に1回に制限するなどのときは③を使う。結果を問わず、取りに行ったら③を残す。一定期間内の連打防止用途。

これらの時刻を記録するテーブル:表名（仮）は `symbol_fetch_status`。銘柄1つにつき1行。

| カラム | 中身 |
| --- | --- |
| `symbol_id` | 銘柄。主キー |
| `last_answered_at` | ② 取得先が返事した時刻 |
| `last_attempted_at` | ③ 取りに行った時刻 |
| `review_complete_date` | おさらいの印（その日以前は、1ヶ月経ったあとの取り直し済み） |

`daily_bars` には足さない。


## 4. 「もう閉まっている最新の営業日」

「カレンダー上の今日」ではない。市場が開いている最中の今日は、確定日足には使わない。

意味は: その市場の現地時間で、大引けから少し待ったあと、「確定が出ているはず」とみなせる最新の営業日。

待ちは市場単位。東証の例: 15:00大引けのあと、**最初の1回は16:00以降**。15:35から全員を取りに行かない。早すぎると、まだ出揃っていない日に監視銘柄ぜんぶが空になり、毎日その分の取得を使う。

確定日足は、寄付の気配のように銘柄ごとに出揃い時刻がばらつくわけではない。市場ごとにおおよそ同じ頃に出揃う。銘柄ごとに閉場判定はしない。アプリを開く時刻を人ごとにずらすのは、取得先の負荷分散用（既存方針）で、出揃い待ち用ではない。

ごく一部の銘柄だけ遅いことはある。それは市場単位の16:00では拾いきれない。後述の15分再試行で拾う。1〜2銘柄だけ遅れたのに、空の返事でその夜を打ち切って翌日の大引けまで終値が分からない、はおかしい、で合意した。

米国は、その市場の現地の大引け＋同様の待ち。時刻の定数は市場ごとに持つ。

気配の更新ボタンを、同じ時間のあいだに何回も押せる（例: 10時台は1回まで、11時になってからまた1回）。確定日足の大引け後15分区切りと、気配の1時間区切りは別。混ぜない。

## 5. 追いつき処理（最新まで来ているか）

更新ボタン／起動／プレイリスト表示など、日足更新が走ったとき。銘柄ごと。

1. ①（一番新しい日足の日付）を見る  
2. カレンダーで、「もう閉まっている最新の営業日」を見る  
3. 同じなら、追いつき処理は終了（何も取りに行かない）  
4. 違うなら、③を見て、今の15分区切りで既に取りに行っていれば行かない。まだなら取りに行く  
5. 取る範囲は、通常は①の日付から先（その日の再取得も含めてよい。同じ日付は upsert）。①が今日の30日前より古いときは印から。詳細は2/2 §11  
6. 取りに行ったら、結果に関わらず③を更新する  
7. 取得先が返事したら（0件でも）②を更新する。通信エラーなら②は触らない  

「直近営業日の閉場以降に②があれば、もう確認したとみなして終了」という最初の案は、**空の返事でその夜を打ち切ってしまう**ので採用しない。

通信エラーで②を進める案も不採用。失敗なのに「もう確認した」になり、次の大引けまで取り直さない。

空と失敗の見分け:

- 普通に返ってきたが、その日の足が0件 → 空（国葬など）。②を更新する。③も更新する  
- つながる前に落ちた、時間切れ、エラー番号 → 失敗。②は触らない。③は更新する。確認済みの空にはしない  

①の日付が、今日の30日前より古い場合: 関数B（おさらい）は別に呼ばない。印から今持っているべき日まで1回取る。その間の日はカレンダーの休みも含めて取得先に聞く。返ってきた足は全部入る。成功したら印を今日の30日前にする。詳細は2/2 §11。

## 6. 大引け後の15分再試行（遅い銘柄用）

東証の例（他市場は同じ考え方で時刻だけ変える）:

- 最初の1回: 16:00以降  
- そこで足が来た銘柄: 終わり  
- 来なかった銘柄だけ: 17:00まで、15分に1回、もう一度取りに行ってよい  
  例: 16:00〜16:15、16:15〜16:30、16:30〜16:45、16:45〜17:00  
- 17:00を過ぎたら、その日は打ち切り  
- 「この15分に行ってよいか」は③。結果が何でも、その区切りは1回  

15:30のあと15:35から15分ごと、のように開始を早める案は不採用（全員が空になり取得を使う）。

空のときは②を進めてよいが、それで夜を打ち切らない。打ち切りは「17:00を過ぎた」と③。

17:00までに来れば、遅い銘柄もその日のうちに終値が出る。17:00までに来なければ、その夜は終わる。

## 7. 翌日以降: 追いつきと、途中の穴は別処理

月曜の足が17:00までに来なかったとする。手元の一番新しい日足は、まだ金曜のまま。

**火曜の大引け直後（16:00）:**

- ①はまだ金曜  
- 「もう閉まっている最新営業日」は火曜  
- まだ最新に追いついていない → この1回は追いつき処理。「金曜から先」を取りに行く  

ここで火曜の足が来る。月曜も来れば終わり。月曜だけ来なければ、その瞬間に①は火曜になり、月曜が途中の穴になる。

**そのあと（次の更新、または同じ回の見比べ）:**

- 最新は揃っている（火曜＝カレンダーの最新）  
- 月曜だけ無い → 追いつき処理は走らない（①と最新が同じだから）  
- ここで初めて、カレンダー diff の穴埋め: 手元のカレンダーと手元の日足を見比べ、欠けた日だけ取りに行く  

「翌日の大引け後はもう穴だから diff だけ」は、火曜の足が既に手元にあるあと。火曜の足をまだ持っていない時点では、まだ追いつき処理。火曜の足をまだ持っていないのに diff だけ、と飛ばして書いていたのは誤りだった。

## 8. 途中の穴の見比べ（カレンダー diff）

追いつきは「一番新しい足が、最新の確定営業日まで来ているか」だけ見る。最後が揃っていても、先週の営業日が1日欠けている、は見逃す。途中の穴は別確認。

これは後述のおさらい（1ヶ月経ってから取得先をもう一度聞く）とは別物。名前を混ぜない。

カレンダー diff は2段に分ける。

1. 手元のカレンダーと手元の日足を見比べる（通信しない）  
2. 欠けていた日のうち、「まだ空と確認していない日」だけ、取りに行く  

見比べの条件は「カレンダーは営業日（`is_trading_day = 1`）なのに、`daily_bars` に無い」。休みと書いてある日は、この diff の対象外。1/2 に書いた「カレンダーは休み、取得先には足がある、手元には無い」パターンは、ここでは拾わない（おさらい側の話）。

1は端末の中の照合。監視100銘柄・10年でも体感は一瞬のことが多い。更新ボタンのたびに走らせてよい。重いのは2の、Yahoo 等へ取りに行くとき。

全期間をYahooから取り直す、はしない。欠けが無ければ通信はゼロ。

国葬のように、カレンダーだけ営業日で、何度取っても空、という日は、毎日・毎週取りに行かない。取りに行って0件で返事が来たら、その銘柄のその日は「足は無いと確認済み」と残す。次の見比べでは穴に数えない。fetch はその日について原則1回で終わり。通信エラーの回は「確認済みの空」にしない（また取りに行けるようにする）。

確認済みの空の置き場所は、②（銘柄1つの時刻）とは別。`(銘柄, 日付)` ごと。

カレンダー差し替え後に、営業日フラグが変わった日は、確認済みを見直す必要があるかもしれない。そこは設計書に落とすとき、一言決める。

週1で空と分かっている日を取りに行く案は不採用。空と分かったあとは、1日1回も週1も不要。

## 9. 国葬と遅れの具体例（同じ流れで両方扱う）

その場では区別できない。空でも夜を打ち切らず、15分再試行する。

**遅れ（本当は営業日で、取得先が遅い）:**  
16:00空 → 16:15または16:30で足が来る → ①が進む → 終わり。

**国葬（カレンダーは営業日、実際は休場）:**  
16:00〜17:00は空振り（③で15分に1回）。17:00でその日は打ち切り。火曜16:00の追いつきで火曜の足が来る。月曜は途中の穴。カレンダー diff で月曜を1回取りに行き、空なら確認済みの空。以後取りに行かない。

「次の確定営業日の足まで来たら確認済みの空にする」の意味は、上の国葬の切り替えのこと。月曜の夜に来ず、火曜の足が取れたあと、月曜は「最新に追いついていない」ではなく「途中の1日が欠けている」になる。欠けを1回取りに行き、来れば保存、来なければ確認済みの空。

## 10. おさらい（1ヶ月経ってから、取得先をもう一度聞く）

### 前提

後から空白だったところに穴が埋まるのは、長くてもおおよそ1ヶ月以内、とする。2ヶ月前の日にいきなり足が生える前提は置かない。

初めてその銘柄の履歴を取るときに、取得先が持っていた日は入っている。何年も経って、カレンダーでは休みなのに実際には足があった日が、いきなり過去に入ってくる、は追わない。

印は、久しぶりに開いた人だけのためのものではない。毎日使う人向けの記録でもある。①はもう最新で追いつきが走らない日でも、取得先があとから古い日の足を直したり足したりすることがある。印は「その古い日を、1ヶ月経ってからもう一度聞いたところまで」を残す。

月1回「直近30日を全部取り直す」をユーザーIDの30等分でずらす案は不採用。印（日付1欄）で足りる。

### 印: 穴埋めチェック完了日（仮の呼び方）

銘柄ごとに日付を1欄持つ。別サービスは不要。日足更新のときに見る。その銘柄の取得が失敗したら、その銘柄の印は進めない。

②や③（時刻）とは別で、日付。意味は「この日以前は、1ヶ月以上経ってから、取得先にもう一度聞いた」。

カレンダー diff（営業日なのに足が無い）とは別。名前を混ぜない。設計書に落とすとき、混同しない名前にする。

### 印の進め方（具体例。この日付で固定）

**8月10日に、半年ぶり（①＝2月10日、印＝1月11日頃）に開く。**

- ①（2月10日）は、今日の30日前（7月10日）より古い → 関数Bは呼ばない  
- 追いつき1回: 印（1月11日頃）から今持っているべき日まで  
- 1月12日〜2月9日はDBにあっても、印より先でまだおさらい未完了の帯。印から取ればここも含まれる  
- 8月1日分を8月10日に「おさらい完了」にしてはいけない。まだ1ヶ月経っていない  
- 成功したら印を7月10日にする  

**4ヶ月空いて、12月10日に開く（①＝8月10日、印＝7月10日）。**

- ①（8月10日）は、今日の30日前（11月10日）より古い → 関数Bは呼ばない  
- 追いつき1回: 印（7月10日）から12月10日まで  
- 7月11日〜8月9日も、印から取ればおさらい未完了分を含めて更新される  
- 成功したら印を11月10日にする  

**次に12月25日に開く（①＝12月10日、印＝11月10日）。**

- ①（12月10日）は、今日の30日前（11月25日）より後（＝今日の30日以内） → 関数Aと関数Bの両方  
- おさらい（関数B）: 印（11月10日）の次の日から11月25日まで。印を11月25日にする  
- いつもの更新（関数A）: 12月10日から12月25日  
- 11月25日〜12月10日の間はもう持っている日。区間が空くので、1本にまとめない  
- 12月10日から25日の新しい分は、まだ1ヶ月経っていないので、おさらいの対象外  

### 取る範囲（おさらい関数）

おさらいを、アプリを開くたびに「印から今日まで」取ると、毎日使う人は毎日、直近1ヶ月を全銘柄取り直す。重い。不採用。

おさらいが取るのは **印の次の日から、今日の30日前（1ヶ月前）まで** だけ。今日の1ヶ月前より新しい日は、この処理では見に行かない。

毎日開くなら、1日分だけが新しく1ヶ月経つので、その1日だけ足す。12月25日、印が11月10日なら、11月11日から11月25日まで。

①が今日の30日前より古いとき（8月10日・12月10日の例）は、関数Bは別に呼ばず、関数Aの1回で印から取る。関数B単独で「新しく1ヶ月経った区間」が長くなるのは、①が今日の30日以内で毎日使う場合の話。

8月10日時点で8月1日をこのおさらいで見に行っても、まだ1ヶ月経っていないので意味が薄い。1ヶ月経った状態のときに見る。

## 11. DailyBarService の中は手順が2つ（サービスは1つ）

サービスは日足更新ひとつ（`DailyBarService`）。中の手順は二つに分ける。一つの関数に詰めない。サービスを二つにはしない。呼び出し側が二重になり、失敗したときの印の進め方も分かれる。

中身が違うから分ける。

### ①と今日の30日前を比べる（関数A／Bの呼び方）

①の日付が、今日の30日前より古い:

- 関数B（おさらい）は別に呼ばない  
- 関数Aで、印から今持っているべき日まで1回取る  
- 成功したら印を今日の30日前にする  

①の日付が、今日の30日以内:

- 関数A: ①から今持っているべき日まで  
- 関数B: 印の次の日から今日の30日前まで（印がもう30日前なら何もしない）  
- 成功したら印を今日の30日前にする  

**関数A（いつもの更新・追いつき）**

- 始点: 通常は①（その銘柄の一番新しい日足の日付）。前回アプリを開いた日ではない  
- ①が今日の30日前より古いときは、関数Bを別に呼ばず、始点を印にする  
- 終点: 今持っているべき日（もう閉まっている最新の営業日）  
- 始点と終点が同じなら、何も取りに行かない  
- ③の15分区切りを見る  
- 16:00開始、17:00まで来なかった銘柄だけ15分に1回  
- ①が今日の30日前より古く、成功したら印を今日の30日前に進める  

**関数B（おさらい）**

- ①が今日の30日前より古いときは呼ばない  
- 始点: 印の次の日  
- 終点: 今日の1ヶ月前  
- 印が今日の1ヶ月前と同じ（またはそれ以降）なら、おさらいは何も取りに行かない  
- 成功したら印を今日の1ヶ月前まで進める。失敗したらその銘柄の印は進めない  

日足サービスがこの二つを呼ぶ。

### 通信を1本にまとめる／まとめない

「①が今日の30日前より古い」ときは、もともと1本で済む。関数Bは呼ばない。

「①が今日の30日以内」のときだけ、関数Aと関数Bの区間を見比べる。

区間が重なる／つながるとき:

- 古い方の始まりから今持っているべき日までを1回で取ってよい  
- この判断は、まとめる側（日足サービス）の仕事  

区間が空くとき（12月25日など: おさらい11月11日〜11月25日、いつもの更新12月10日〜12月25日）:

- まとめない  
- 間（11月25日〜12月10日）はもう持っている日。1本にすると、持っている日まで取り直し、「毎回1ヶ月分」の無駄になる  
- 通信の回数より、取らなくてよい日を取り直す方が無駄  
- おさらいと、いつもの更新は、別の期間のままそれぞれの関数が取る  

「重ならないときも11月10日から12月25日を1回」は不採用。以前「毎日1ヶ月分は重い」と言ったことと食い違っていた。正しいのは、重ならないときは分けたまま。

### 異常時（①と印の関係が壊れているとき）

追いつきだけ失敗して、印だけ進み、印の日付が①より新しくなっているときは、①から取る。上の具体例（8/10、12/10、12/25）とは別の話。

## 12. 既存の `DailyBarService` との接続（現状の正本）

`01_Data_Layer.md` にある今のスキップは、おおむね次。

- `daily_bars` の最新 `trade_date` と、「想定される最新の確定営業日」を比べる  
- 揃っていれば取りに行かない。足りなければ不足分だけ取る  
- きっかけはユーザ操作（起動、プレイリスト、デッキ、個別チャート）  
- 定時の強制一括取得は作らない  
- 気配は時間枠（例: 10時台は1回まで）。`latest_snapshots.updated_at` で枠内更新済みならスキップ  

今回決めたことは、この「想定される最新の確定営業日」をカレンダーから出すこと、①②③、16:00開始・17:00まで15分再試行、途中穴のカレンダー diff、確認済みの空、おさらい（穴埋めチェック完了日）、DailyBarService 内の関数A／関数B、重なるときだけ期間を1本にする、を足すこと。

気配の1時間区切りと、確定日足の大引け後15分区切りは別。混ぜない。確定日足の③は、大引け後の再試行と、開き直し連打の防止用。

失敗時の段階的リトライ（一括→失敗分だけ個別→もう一度）はプロトタイプの参考。今回の本文では、③による区切り1回と、空／通信エラーの分けまで合意。段階の本数までは未固定。設計書に落とすとき、既存の「同じ時間枠では1回」と矛盾させない。

更新のきっかけは今どおりユーザ操作。おさらいも、起動やプレイリストを開いたときの日足バッチに乗せる。おさらい専用の別バッチ・別サービスは作らない。ユーザーがアプリを開く日が人ごとに違うので、自然にずれる。同じ人の監視銘柄が同じ日にまとまっても、おさらいが「新しく1ヶ月経った分だけ」なら、毎日使う人は1日分程度。
