## 1. 方針転換: カレンダーを持つ



### 以前の方針（廃止する）

祝日カレンダーは自前で持たない。取得先に聞いて、返ってきた日だけを信じる。祝日で何も返らなければ何も保存しない。プロトタイプも土日以外の祝日は無視していた。

### 変える理由

確定日足の更新は、次が必要になる。

- 手元の一番新しい日足は、どの日付か  
- 「いま持っているべき、もう閉まっている最新の営業日」はどの日付か  
- 古ければ、足りない分を取りに行く

カレンダーが無いと、次の区別がつかない。

- 休場だから無い  
- 通信に失敗したから無い  
- 途中の営業日の足が欠けている

欠けると、その銘柄だけ日足の並びが詰まり、チャートがずれる。休場日を休場と分からないと、足が無いのは祝日のせいなのに「まだ最新に追いついていない」と判定し、同じ日を何度も取りに行く。以前カレンダーを避けた主因は再配布だった。白寄りと分かったので、カレンダーを持つこととする。

### カレンダーの役割と、値段の正本

- 値段の正本は取得先。返してきた足だけ保存する。カレンダーが休みと書いていても、取得先が足を出せば保存する。カレンダーで間引いて捨てない  
- カレンダーは「取りに行く／行かない」「欠けと休場を分ける」ための目安。値段の正本にはしない

カレンダーが外れる日はある。

**営業日と書いてあるのに休場（国葬、台風、急な祝日）**  
取りに行って空が返る。こういう日は稀なので、カレンダーが実態とずれていても許容する。ただし、同じ日を無限に取りに行かない（§5・§11 のロックによる fetch 間隔。後述）。

**休みと書いてあるのに開いている（カレンダー遅れ、誤記）**  
より性質が悪い。カレンダーを信じて取りに行かないと、その日の足が永久に欠ける。

これから先（最近の分）の防ぎ方: 追いつき取得は「予想の1日だけ」ではなく「`review_complete_date` の翌日から先」を期間でまとめて聞く。この区間の中なら、カレンダーが休みと書いてある日も、取得先が足を出せば返ってくる。返ってきたら保存する。

例: カレンダーは月曜休み。実際は開いていた。`review_complete_date` は11月25日（前回照合済み）。火曜の大引け後、11月26日から先を取る。その中に月曜が入る。取得先が月曜を出せば保存される。

昔の分（一番新しい足より前で、カレンダーは休み、取得先には足がある、手元には無い）: レビュー（§10）でも見つからない。レビューが取りに行くのは `review_complete_date` の翌日から先だけで、それより前の日は取りに行かない。

何年も前の日に、あとから足が生える前提は置かない。初めてその銘柄の履歴を取るときに、取得先が持っていた日は入っている。例えば半年などのかなり古い日の空白が、`review_lookback_days` 以上経ってから突然埋まる、は想定しない。代わりに、取得先があとから直す・足すのはおおよそ `review_lookback_days` 日以内、という前提で設計する。`review_complete_date` より前の古い日は、`review_lookback_days` ごとの定期照合の対象にもならない（§10）。

### チャートの欠け

週足・月足は、日が1日欠けても「穴の足」としては見えにくい（1本にまとまる）。中身の高安・出来高は少し狂い得るが、見た目の穴にはならない。問題は日足チャート。

表示は、証券アプリと同じく**営業日の足だけ右に詰める**。欠けた営業日を空白で1本飛ばさない。空白は休場に見えて分かりにくい。正しい対処は、表示で穴を空けることではなく、検知して取り直して埋めること。埋まるまでは詰めたまま出す。

## 2. カレンダーの中身と自動差し替え



### テーブル案 `market_calendar`

「営業日だけを並べる」のではない。対象期間の**暦日を全部**入れ、営業日フラグを付ける。営業日だけだと、途中欠損と休場の区別がつかない。


| 列                | 意味                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `country`        | `JP` / `US`                                                                                  |
| `trade_date`     | `YYYY-MM-DD`。対象期間の全日                                                                         |
| `is_trading_day` | 1=営業日、0=休場                                                                                   |
| `day_type`       | その日の種類。例: `regular`（通常営業日）、`half_day`（短縮取引）、`closed`（休場）。決め打ちの2種・3種にしない。あとから種類を増やせる自由な文字列にする |
| `source`         | 例: `pandas_market_calendars`                                                                 |
| 主キー              | `(country, trade_date)`                                                                      |


ファイル全体に `version`（または作った日時 `generated_at`）を付ける。

生成は Python の `pandas_market_calendars`（MIT）。JPX と NYSE。過去〜未来の長期分。出力は上記の形の JSON（または同等）。人が毎年思い出す作業にはしない。スクリプトで生成する。

行数は少ない（例: 40年×2カ国でも数万行）。端末に置いても軽い。


### テーブル案 `market_boundary_points`（境界点。DB管理）

`update_daily_bars` / `update_snapshot` のロック（`daily_bar_locked_until` / `snapshot_locked_until`）を、いつまでにするかを決めるための、時刻の点の一覧。`market_calendar` とは別のテーブル。

値は運用しながら細かく調整したい（市場ごとに違う、データ取得先ごとに違う、寄付き直後だけ間隔を短くしたい、など）ので、`market_calendar` のような静的ファイルではなく、**DB で持つ**。

境界点1つが1行。「`daily_bar` 用」「`snapshot` 用」という区別はこの表に持たせない。どの点をどの処理が使うかは、呼び出し側（`update_daily_bars` / `update_snapshot`）が決める。データ取得先（`source`）が違えば、同じ国・`day_type`でも時刻は別の行になる（例: 同じJPでも `yahoo` と `jquants` は別々の時刻を持てる）。現時点では `yahoo`・JP 分のみ値を用意し、他ソース・他国は未調査のため保留。

| 列 | 意味 |
| --- | --- |
| `source` | データ取得先。例: `yahoo` / `jquants` / `eodhd` |
| `country` | `JP` / `US` |
| `day_type` | `market_calendar.day_type` と対応 |
| `time` | `HH:MM`。この時刻が1つの境界点。**採用：現地時間**（JPは`Asia/Tokyo`＝JST、USは`America/New_York`＝ET。プロトタイプはJSTへの統一をせず、各市場の現地時間で一貫して判定していた） |
| `name` | 任意。単体で名前を付けて直接指したい点だけ付ける（例: `session_close_time`）。付けなくてよい |
| 主キー | `(source, country, day_type, time)` |



`day_type = closed` の日は境界点を引かない（そもそも処理が走らない）。

### テーブル案 `market_boundary_boxes`（境界点をまとめる箱。DB管理）

境界点とは別の、独立したテーブル。箱は「開始〜終了の時刻の範囲」を持つだけで、中の境界点を紐付けて保存しない。「この箱の中にある境界点」は、使うときに時刻の範囲で検索して決める（例: `AM_Box` が9:00〜11:30なら、9:00〜11:30の境界点が対象）。

箱が重なってもよい（例: 9:00〜10:00の箱Aと、9:30〜11:30の箱Bが両方あってもよい）。境界点は紐付けを持たないので、両方の箱から同じ点が見える。


| 列 | 意味 |
| --- | --- |
| `source` | データ取得先。例: `yahoo` / `jquants` / `eodhd` |
| `country` | `JP` / `US` |
| `day_type` | `market_calendar.day_type` と対応 |
| `name` | 箱の名前（例: `AM_Box`） |
| `start_time` | `HH:MM`。箱の開始 |
| `end_time` | `HH:MM`。箱の終了 |
| 主キー | `(source, country, day_type, name)` |


### 境界点の選び方（呼び出し側が決める。表には持たせない）

`daily_bar_locked_until` / `snapshot_locked_until` にセットする値をどう決めるかは、呼び出し側（`update_daily_bars` / `update_snapshot`）が、次のどちらかを選ぶ。組み合わせの決め方自体は表に持たせない。

**箱を指定するやり方**

プログラム側が「今の時刻が、この国・`day_type`・この箱（開始〜終了）に該当するか」を判定し、該当するときだけその箱を指定して呼ぶ。該当する箱の中で、今より後の一番近い境界点を使う（例: 9:40の時点で `AM_Box`（9:00〜11:30）に該当 → 9:40より後で一番近い境界点を使う）。該当しない時刻では、そもそもこの箱を指定しない。

**名前で1点を直接指すやり方**

例: `daily_bar_reflect_time` という境界点そのものを使う。この場合は「今日の点」だけでなく、「基準の日から何営業日後の点か」を指定できる（`market_calendar` で営業日を数える）。例: 「1営業日後の `daily_bar_reflect_time`」「2営業日後の `daily_bar_reflect_time`」。

例（確定日足が17:00に取れて、次のロック解除を決めるとき）: 1営業日後の `daily_bar_reflect_time` を指定する。これが次の営業日の20:30になる。

例（初期値のイメージ。`yahoo`・JP の場合。実際の値は運用しながら調整する。他ソース・他国は未調査のため保留）:

- `yahoo`・JP・`regular`・`AM_Box`（9:00〜11:30）の中に、9:00, 9:10, 9:20, 9:30, 10:00, 10:30, 11:00 … の境界点。`update_snapshot` は、今の時刻がこの箱に該当するときだけこの箱を指定して次の点を使う。寄付き直後は間隔を短く、落ち着いたら広げる
- `yahoo`・JP・`regular`・`daily_bar_reflect_time`（20:30）という名前の境界点。`update_daily_bars` のロック解除は、この点の1営業日後を直接指す（§11）
- `yahoo`・JP・`regular`の、その他の名前付き境界点: `session_open_time`（9:00）・`quote_rollover_time`（8:45）・`am_session_close_time`（11:30）・`pm_session_open_time`（12:30）・`close_confirm_time`（18:30）・`daily_bar_reflect_time`（20:30）。用途・値の根拠は別途メモ（次の項）

### 境界点の自動生成（`fixed_interval`。管理画面用の道具）

「9:00〜11:30に10分おきで境界点を作る」のように、決まった間隔で境界点をまとめて作る道具。作った後は、ふつうの境界点（`market_boundary_points` の行）として保存され、選ぶときの扱いも他の境界点と同じ。間隔を変えたいときは、その範囲の境界点を作り直す。

### `trigger_interval`（操作トリガーからの間隔。境界点・箱とは別の仕組み）

「エラーが起きてから3分待って再試行する」のような、操作・イベントの時刻を起点にした相対時間。あらかじめ時刻の点として決めておけないので、境界点・箱のテーブルには入れない。別の、その場で計算する仕組みとして持つ。

用途は、**配信元側のエラー**が起きたときに、短い間だけロックして、次に試すまでの待ち時間を作ることだけ（§5「失敗時の扱い」）。デバイス側・通信環境側のエラー（機内モード、電波不良など）のときは使わない（fetchを消費していないため、ロックせずリトライ無制限でよい）。`daily_bar_locked_until` / `snapshot_locked_until` 本体の判定（絶対時刻ルール）はこれで置き換えない。通常サイクルのロックは、引き続き境界点・箱による絶対時刻のみで判定する。


### 自動差し替え（人手なし。後回しにしない）

年1回、人が手で差し替える前提にはしない。忘れる前提で、人が介在しない道を今の設計に含める。

サーバーがまだ無くても、アプリ側の更新の流れは後から変えない。最初は、カレンダーファイルをアプリに入れて配る（サーバーは使わない）。置き場がサーバーになっても、version の比較と差し替えだけで済むようにする。
いつもの日足取得・判定で使うのは、常に手元のカレンダー。サーバー（または配信 URL）に行くのは、カレンダー本体の更新確認・差し替えのときだけ。

1. カレンダーに `version`（または作った日時）を付ける
2. 起動時（または定期）に、手元の `version` と配信側の `version` を比べる（サーバーが無い段階ではこの確認はスキップしてよい）
3. 配信側の方が新しければ、手元のファイルを差し替える
4. 失敗・オフラインならエラーにせず、手元のまま動かす

生成バッチをサーバーで定期実行し、静的ファイルとして公開する形も、今の設計に含めておく。サーバーを置いたときにそのまま使える。

端末に `pandas` や `pandas_market_calendars` は載せない。生成はサーバー（またはビルド時）。端末は出来上がった表を持つだけ。

### 調査メモ：Yahoo取得元とタイムゾーンの仕組み（0824調査、プロトタイプ実装を確認）

※ 以下はプロトタイプの実装を調べた参考情報。新アプリの実装をこの通りにする、という決定ではない。

調査対象：`SwingDeck_prototype`（Pythonアプリ）と `SwingDeck_prototype/notes/スレッド引き継ぎ/GS全文.txt`（GoogleシートGAS）の実装コード。

1. **Yahoo!の取得先は世界共通で1つ。`yahoo_japan`・`yahoo_us`という別々のAPIは存在しない**
   両プロトタイプとも、JP銘柄（`7203.T`）・US銘柄（`AAPL`）どちらに対しても、同じ1つのURL（`https://query1.finance.yahoo.com/v8/finance/chart/`）にティッカー名だけ変えてアクセスしている。取得元を国別に分けるコードは無い。（消費者向けサイト `finance.yahoo.co.jp` とは別物で、データ取得には使われていない）
   → 境界点テーブルの `source` は `yahoo_japan`/`yahoo_us` ではなく `yahoo` に統一し、JP/USの違いは既存の `country` 列で表す（本ファイル内の該当箇所は対応済み）。

2. **サマータイムは、絶対時刻→現地時刻への変換をその都度行うだけで、手動計算していない**
   銘柄ごとに「どの取引所のタイムゾーンか」をIANA名で持つ（JPは `Asia/Tokyo`、USは `America/New_York`）。日足の `trade_date` やスナップショットの `session_trade_date` を決めるときは、APIが返す絶対時刻（UTC）をこのタイムゾーン名に変換してから日付を取り出す（Python: `astimezone(ZoneInfo(...))`、GAS: `Utilities.formatDate(..., tz, ...)`）。サマータイムかどうかの判定はこの変換の中で自動的に行われ、年2回の切替を手動で判定するコードは存在しない。

   参照ファイル：`app/utils/market_time.py`, `app/clients/yahoo_client.py`, `app/utils/yahoo_daily.py`（GAS側は `getMarketToday_` / `extractPrevClose_` 関数など）

3. **`country`（JP/US）を決めるときは、APIの実データを優先する**

   GASの`resolveMarket_`は、`currency`（実データ）が`JPY`/`USD`ならそれを最優先し、空欄のときだけティッカーの見た目から推測する（`isJapaneseTicker_`）というフォールバック順になっていた。Pythonプロトタイプ側も`symbols`テーブルに`market`列を別途保持している。

   → 新しい設計でも、銘柄登録時にAPIが返す実データ（`exchange`/`currency`/`market`など）から`country`を確定してDBに保存し、以降はDBの値を使う。ティッカーの見た目（`.T`が付いているか、数字が入っているかなど）からの推測は使わない（銘柄登録処理自体の設計はここでは未着手。別途検討）。

4. **`market_time.py`（絶対時刻→現地時刻の変換ユーティリティ）の置き場所と呼ばれ方**（3とは別の話）
   これは国判定の話ではなく、「今何時か・今日は何日か」を各市場の現地時間で判定するための、データ取得層の小さいユーティリティの設計の話。`indicators.py`（計算工場。MA/EMA/RSIなど価格の計算専用）とは別物で、そちらには含めない。
   プロトタイプでは `app/utils/market_time.py` という独立ファイルに置かれ、`update_daily_bars` / `update_snapshot` を実装するサービス（`price_service.py`など）側が、その中の関数を呼び出して、返ってきた値（現地の「今日の日付」など）を使って自分の判定を続ける、という関係だった。

   ```python
   from zoneinfo import ZoneInfo

   def exchange_timezone_for_ticker(ticker_api: str) -> str:
       return "Asia/Tokyo" if is_jp_ticker(ticker_api) else "America/New_York"

   def market_today_for_ticker(ticker_api: str) -> date:
       return market_today(exchange_timezone_for_ticker(ticker_api))

   def market_today(exchange_timezone: str) -> date:
       return _exchange_local_now(exchange_timezone).date()

   def _exchange_local_now(exchange_timezone: str) -> datetime:
       return datetime.now(ZoneInfo(exchange_timezone))
   ```

   → 置き場所は `indicators.py` ではなく `01_Data_Layer.md` 側（Data Fetcher周り）が自然。呼ばれ方は「アプリ起動時に1回」ではなく、`update_daily_bars` / `update_snapshot` などが呼ばれるたびに、その都度内部で呼び出す（今の時刻は変わり続けるため、キャッシュして使い回すことはできない）。反映は`0819`完成後にまとめて。


## 3. 確定日足の取得で使う記録（`latest_bar_date`・`last_answered_at`・`last_attempted_at`、`review_complete_date`）

### `latest_bar_date`（手元の一番新しい日足の日付）

`daily_bars` に、その銘柄の足が何本入っているかは銘柄ごとに違う。そのうち **いちばん新しい** `trade_date` が `latest_bar_date`。列としては保存せず、`daily_bars` から都度 `MAX(trade_date)` で出す。

`update_daily_bars` の始点は `latest_bar_date` ではなく、`review_complete_date` の翌日（§5）。「前回アプリを開いた日」でも、「今日の日付」でもない。

例（どちらも12月10日にアプリを開く）:

- 大引け前に開く … 10日分はまだ確定していない。取れたのは9日まで → `latest_bar_date` は12月9日。
- 大引け後（`session_close_time` 以降）に開いて、その回で10日分まで取れた → `latest_bar_date` は12月10日。

`latest_bar_date` が進むのは、アプリを開いたからではなく、取りに行って足が保存されたとき。いつ開くかと、`latest_bar_date` が何日かは一致しない。

### `last_answered_at`（取得先が返事した時刻）

取得先がエラーなく答えたときだけ記録される。中身が0件でもよい。通信エラー・時間切れでは記録されない。

使い道は連打防止ではない。あとから「この日は足が無いと、取得先が空で答えた」とみなすとき用。
置き場所は、下記の `symbol_fetch_status` を参照。

### `last_attempted_at`（取りに行った時刻。結果を問わない）

`update_daily_bars` が fetch に行った時刻。足が来た／0件／通信エラー、のどれでも残す。アプリを閉じても残る。

使い道は連打防止の判定には使わない。`update_snapshot` の連打防止は `snapshot_locked_until` で行う（§3.5・§6）。`update_daily_bars` は、成功後は2条件（レビュー期限超過・ギャップ2営業日以上）が非該当になることで連打防止される。ただし、1回のfetch実行中（開始から結果が返るまで）に複数回呼ばれた場合の重複防止はまだ仕組みが無い（未設計。実行中の多重呼び出しガードが別途必要）。ログ・観測用として残す。

`update_snapshot` の取得時刻は `latest_snapshots.updated_at` に残す（同様にログ用。`symbol_fetch_status` には載せない）。

### `symbol_fetch_status`（銘柄1行）

表名（仮）は `symbol_fetch_status`。銘柄1つにつき1行。


| カラム                      | 中身                                                           |
| ------------------------ | ------------------------------------------------------------ |
| `symbol_id`              | 銘柄。主キー                                                       |
| `last_answered_at`       | 取得先が返事した時刻                                                 |
| `last_attempted_at`      | `update_daily_bars` が取りに行った時刻                              |
| `review_complete_date`   | その日以前は、`review_lookback_days` 経過後に本物の確定履歴で照合済み（§10）          |
| `daily_bar_locked_until` | `update_daily_bars` をスキップする期限。確定足取得成功後、翌営業日の `daily_bar_reflect_time` 頃まで（§3.5） |
| `snapshot_locked_until`  | `update_snapshot` をスキップする期限。確定足取得成功後、翌営業日の `quote_rollover_time`（8:45）まで（§3.5）   |


`daily_bars` には足さない。

### `review_lookback_days`（おさらいの遡及日数）

`update_daily_bars` の始点・定期照合の基準になる暦日数。定数（可変）。初期値は 30。

「今日の `review_lookback_days` 日前」= 実行日の日付から `review_lookback_days` 日引いた日（`YYYY-MM-DD`）。

### `review_trigger_multiplier`（定期照合を発動させる倍率）

定期照合（§10）を発動させるかどうかの基準日数を決める倍率。定数（可変）。初期値は 2。

発動の基準日数 = `review_lookback_days` × `review_trigger_multiplier`（初期値なら 30 × 2 = 60日）。`review_complete_date` からこの日数以上経っていたら、定期照合として `update_daily_bars` を呼ぶ（§10・§11）。

`review_lookback_days` 自体（＝直近何日分をまだ確定扱いにしないか）とは別の値。混同しない。

## 3.5 `daily_bars` と `latest_snapshots`（確定日足と snapshot）

配信元（Yahoo 等）では、**気配・現在値** と **日足履歴** は別の取り方になる。SwingDeck も保存先を分ける。


|                 | 確定日足                   | snapshot（その日の仮足）                  |
| --------------- | ---------------------- | --------------------------------- |
| 保存先             | `daily_bars`           | `latest_snapshots`                |
| Adapter         | `fetch_daily_bars`     | `fetch_snapshot`                  |
| DailyBarService | `update_daily_bars`    | `update_snapshot`                 |
| 中身              | 大引け後に確定した営業日の OHLCV。不変 | その取引セッションの進行中 OHLCV。上書き更新         |
| ユーザーが欲しいもの      | 新しい**確定日足**            | 場中チャートの**いまの足**、インディケータ・フィルター計算の元 |


15:30 頃に証券アプリで見える終値は、配信元の quote 系（≒ snapshot 側）であることが多い。`fetch_daily_bars` で今日の1本が返るタイミングは、それより遅いことがある。詳細は §5・§11。

### きっかけと呼び出し順

価格更新ボタン／アプリ起動／プレイリスト表示／デッキ表示など、ユーザ操作のたびに、監視銘柄について `DailyBarService`（`update_snapshot` → 条件により `update_daily_bars`。順番と条件の詳細は §11）を走らせる。

1. `update_snapshots_for_watchlist` … 監視銘柄をまとめて `update_snapshot` の入り口を呼ぶ。`fetch_snapshot` 自体は銘柄をまとめて1回で呼ぶ（§6）。銘柄ごとの判定・後処理は銘柄ごとに行う
2. 銘柄ごとの内部の順番・フォールバック条件は §11 のとおり

個別チャート表示時は、対象1銘柄だけを `fetch_snapshot` に渡し、同じ `DailyBarService` の流れ（§11）。

新しいサービスは作らない。DailyBarService の既存メソッド名を使う。

### `update_daily_bars` の中身

`update_daily_bars` 自体の中身（始点終点・成功時の処理）は §5。呼ぶかどうかの判定（§11 ステップ2の2条件）と、`DailyBarService` の中でいつ呼ばれるか（`update_snapshot` との順番）は §11。

### 確定足が取れたあと（snapshot との関係）

ある銘柄の、その日の確定足（例: 12/10）が `daily_bars` に入ったら（`update_daily_bars` の本物の取得でも、`update_snapshot` からの転記＝§11 でも、どちらでも同じ）:

- その銘柄の `latest_snapshots` 行を**削除**する（同じ日付の仮足を残さない）  
- `update_snapshot` **は、次の取引セッションの `quote_rollover_time`（東証 8:45）までスキップ**する（`snapshot_locked_until`。§3 の表）  
- `daily_bar_locked_until` **を、翌営業日の `daily_bar_reflect_time`（20:30）にセットする**（§3 の表。この値の扱いは次項「fetch の間隔」参照）

例: 12/10 17:00 に 12/10 の確定足が入った → snapshot 削除。`update_snapshot` は 12/11 の `quote_rollover_time`（8:45）までロック。`daily_bar_locked_until` は 12/11 の `daily_bar_reflect_time`（20:30）にセットされる。`update_daily_bars` は、§11 ステップ2の2条件（レビュー期限超過・ギャップ2営業日以上）に該当した時点で呼ばれる（12/11 の確定足用）。

### fetch の間隔（銘柄ごと）

`last_attempted_at` / `latest_snapshots.updated_at` からの相対時間では判定しない。判定するのは `daily_bar_locked_until` / `snapshot_locked_until` という絶対時刻。ただし `update_daily_bars` は、§11 ステップ2の2条件（レビュー期限超過・ギャップ2営業日以上）に該当するときは、このスキップよりも優先して呼ばれる。

- `update_daily_bars` … `daily_bar_locked_until` より前ならスキップ。ただし、§11 ステップ2の2条件に該当する場合はスキップしない  
- `update_snapshot` … `snapshot_locked_until` より前ならスキップ

この2つの値は、`market_calendar` の `day_type` と境界点（`market_boundary_points`。§2）から決まる境界時刻。市場ごと・時間帯ごとに間隔を変えられる（例: 寄付き直後は短く、落ち着いたら長く）。

スキップ判定があるので、ボタンを連打しても、上記より多く fetch しない。


## 5. `update_daily_bars`（確定日足の取得本体）

`DailyBarService` が銘柄ごとに呼ぶ、確定日足取得の本体（呼び出し順は §11）。ユーザーが欲しいのは **新しい確定日足** が主で、ここがその本体。

`catch_up_daily_bars` / `review_daily_bars` という別々の関数には分けない。始点の決め方が違うだけで、やることは「期間を指定して `fetch_daily_bars` を呼ぶ」の1つなので、`update_daily_bars` という1つの関数の中で扱う。

### スキップ（呼び出し側で判定）

`update_daily_bars` 自体はスキップ判定を持たない。呼ぶかどうかは呼び出し側（§11 ステップ2の2条件）が判断する。


### 手順

1. **始点**を決める：`review_complete_date` の翌日（初めて取る銘柄で `review_complete_date` が無ければ、取得先にある全期間が始点）
2. **終点**を決める：今日
3. 始点と終点が同じなら終了
4. 始点〜終点を `fetch_daily_bars` で期間取得する
5. 取りに行ったら、結果に関わらず `last_attempted_at` を更新する
6. 取得先が返事したら（0件でも）`last_answered_at` を更新する。通信エラーなら `last_answered_at` は触らない



### 成功したとき（その銘柄）

- 返ってきた足を `daily_bars` に upsert する  
- `latest_bar_date` が進む  
- `review_complete_date` を、今日の `review_lookback_days` 日前に書き換える  
- 終点の日の確定足（例: 12/10）が入ったら、§3.5 どおり `latest_snapshots` を **削除** し、`snapshot_locked_until`（翌営業日の `quote_rollover_time`。8:45）と `daily_bar_locked_until`（翌営業日の `daily_bar_reflect_time`。20:30）をセットする



### 空と失敗の見分け

- 普通に返ってきたが、その日の足が0件 → **空**（国葬など）。`last_answered_at` を更新する。`last_attempted_at` も更新する。  
- つながる前に落ちた、時間切れ、エラー番号 → **失敗**。`last_answered_at` は触らない。`last_attempted_at` は更新する。

「直近営業日の閉場以降に `last_answered_at` があれば、もう確認したとみなして終了」という案は、**空の返事でその夜を打ち切ってしまう**ので採用しない。

通信エラーで `last_answered_at` を進める案も不採用。失敗なのに「もう確認した」になり、次の大引けまで取り直さない。

### 失敗時の扱い（エラーの種類で分ける）

`update_daily_bars` が失敗したときは、エラーの種類によって次の2つに分かれる（切り分け方法は別途詰める）。

- スマホやPCなどのデバイスの不具合、またはネット環境の障害等に起因するエラーの場合は、そこでDailyBarServiceの処理は終了する。配信元に届いておらずfetchを消費していないため、リトライの制限は必要ない　
- Yahoo!・EODHD・Jクオンツなど、データ配信元側の何らかの原因によるエラーの場合は、`trigger_interval`（§2）で規定の期間ロックを実施する。`DailyBarService` の処理はその時点で終了する。ロックの長さは別途詰める

`update_snapshot` が失敗したときも同じ扱い（§6）。

### 未決点：実行中の多重呼び出しガード

`update_daily_bars` / `update_snapshot` とも、成功後の連打防止（daily_barsは2条件が非該当になること、snapshotは`snapshot_locked_until`）とは別に、1回のfetch実行中（呼び出し開始〜結果が返るまで）に同じ銘柄へ重複して呼ばれた場合の防止策がまだ無い。名前・設計とも未着手。

## 6. `update_snapshot`（snapshot 取得）

`DailyBarService` が銘柄ごとに呼ぶ、最初の処理（§11）。判定・後処理は銘柄ごとだが、`fetch_snapshot` の呼び出し自体は複数銘柄をまとめて1回で行う（下記）。

### 用途

- 場中の日足チャートの **いまの足**  
- インディケータ・サブインディケータ・フィルターなど、**最新足を元にする計算**  
- 閉場済みのセッションのものが取れたときは、確定日足への転記元にもなる（§11）

確定日足の本物の取得（`update_daily_bars`）とは別。混ぜない。

### `fetch_snapshot` のバッチ化（監視銘柄まとめて1回）

`fetch_snapshot` は `symbol_ids: list` を受け取り、銘柄ごとの結果をまとめて返す形にする（`fetch_snapshot(symbol_id: str)` から変更）。

- `update_snapshots_for_watchlist`（監視銘柄全体を回す入口）は、まず銘柄ごとに `snapshot_locked_until` を見て、ロック中でない銘柄だけを集める  
- 集めた `symbol_ids` をまとめて1回 `fetch_snapshot` に渡す（150銘柄でも1回のAPI呼び出し）  
- 返ってきた結果を銘柄ごとに振り分け、下記「手順」の3以降を銘柄ごとに行う  
- 個別チャート表示（対象1銘柄だけ）のときは、その1銘柄だけをリストに入れて呼ぶ（他の監視銘柄とはまとめない）  
- バッチ全体が通信エラーなどで失敗したときは、そのバッチに含まれていた銘柄は全部「失敗」扱いになる（個別の成否分けは、取得先のレスポンス次第で実装時に検討）



### スキップ（取りに行かない）

次の場合、`update_snapshot` は何もしない。

1. `snapshot_locked_until` より前（§3.5・§2の境界点）

その日の確定足（本物の取得でも、snapshotからの転記でも）が `daily_bars` に入っている間は、`snapshot_locked_until` により snapshot は取らない。同じ日付の足は二重に存在しない（§3.5）。

### 手順

1. 上のスキップを確認し、対象の銘柄を集める（バッチ化は上記）
2. `fetch_snapshot` で、集めた銘柄をまとめて取得する
3. 銘柄ごとに、返ってきた結果を `latest_snapshots` に upsert する（`updated_at` を更新）
4. 銘柄ごとに、取得できたsnapshotの対象セッションが、もう閉場しているなら、確定日足として `daily_bars` へ転記する（詳しい手順・判定基準は §11）

### 失敗時の扱い

エラーの種類による分け（デバイス側／配信元側）は §5 と共通（§5「失敗時の扱い」参照）。

### 再試行

`update_daily_bars` / `update_snapshot` とも、境界点（`market_boundary_points`。§2）の時刻ごとに再試行できる。ボタンや起動のたびに処理は **呼ばれる** が、ロック中の銘柄はスキップする。

`session_close_time` に `update_daily_bars` が空振りしても、次の境界（例: `close_confirm_time`〈18:30〉・`daily_bar_reflect_time`〈20:30〉…）で再試行できる（`daily_bar_locked_until` に達する前）。遅い銘柄も、次の境界までに拾う。境界の間隔は境界点（`market_boundary_points`）で決める（初期値のイメージは §2）。
`session_close_time` に `update_daily_bars` が空振りしても、次の境界点で再試行できる（`daily_bar_locked_until` に達する前）。15:30〜20:30の間は境界点の間隔を広めに、`close_confirm_time`〈18:30〉・`daily_bar_reflect_time`〈20:30〉付近はやや細かめに置くイメージ（名前の無い点も複数含む）。遅い銘柄も、次の境界点までに拾う。境界点の間隔は `market_boundary_points` で決める（初期値のイメージは §2）。

## 翌営業日の `quote_rollover_time`（8:45）より前に `update_snapshot` が動き、閉場済みのsnapshotが取れれば §11 の転記で済む。済まなければ `session_close_time` から `update_daily_bars` が動く。



## 7. 途中で1日だけ欠けたときの扱い（レビューでまとめて直る）

月曜の足が、その夜の `update_daily_bars` では来なかったとする。手元の `latest_bar_date` は、まだ金曜のまま。

**火曜、`update_daily_bars` が動く場合（§11 のステップ2）:**

- `latest_bar_date` はまだ金曜
- 火曜のsnapshotが閉場済みになった時点で、`latest_bar_date`（金曜）とsnapshotの日付（火曜）の差が2営業日以上になる → `update_daily_bars` が動く
- `review_complete_date` の翌日から今日までを期間で取得する。ここで火曜の足が来る。月曜も来れば終わり。月曜だけ来なければ、その時点で `latest_bar_date` は火曜になり、月曜が途中の穴になる

**そのあと:**

- `latest_bar_date`（火曜）と、次に取れたsnapshotの日付（火曜）が同じになる → §11 のステップ3は「もう反映済み」に進み、`update_daily_bars` は動かない
- 月曜の穴は、この時点では直さない。次に `update_daily_bars` が動くのは、次にギャップが2営業日以上になったとき、または §10 のレビュー期限が来たときのどちらか
- レビュー期限が来たとき、`update_daily_bars` は `review_complete_date` の翌日から今日までを期間でまとめて取得する。この期間に月曜が含まれていれば、月曜の分もまとめて取りに行く。取得先が月曜の足を持っていれば、ここで埋まる。国葬などで本当に無ければ、空で返ってくるだけ

途中の穴だけを狙って見比べる専用の仕組みは持たない。`review_lookback_days` × `review_trigger_multiplier`（§10）の周期が、そのまま「途中の穴が直るまでの最大期間」になる。この周期を短くすれば、穴が直るまでの期間も短くなる。


## 10. `review_lookback_days` ごとの定期照合

`review_daily_bars` という別関数は無い。`update_daily_bars`（§5）が呼ばれたとき、始点の決め方（`review_complete_date` の翌日）の中に、この「おさらい」の考え方が含まれている。ここでは、それを支える `review_complete_date` の意味と、`update_daily_bars` を呼ぶきっかけについて書く（きっかけの詳細は §11）。

### 前提

取得先があとから古い日の足を直したり足したりすることがある。後から空白だったところに穴が埋まるのは、長くてもおおよそ `review_lookback_days` 日以内、とする（初期値 30。値は可変）。2ヶ月前の日にいきなり足が生える前提は置かない。

初めてその銘柄の履歴を取るときに、取得先が持っていた日は入っている。何年も経って、カレンダーでは休みなのに実際には足があった日が、いきなり過去に入ってくる、は想定しない。

### `review_complete_date`

銘柄ごとに日付を1欄持つ（§3 の表）。意味は「この日以前は、`review_lookback_days` 以上経ってから、取得先にもう一度聞いた」。`update_daily_bars` が成功するたびに、この`review_complete_date`を、今日の `review_lookback_days` 日前に書き換える（§5）。その銘柄の取得が失敗したら、その銘柄の `review_complete_date` は書き換えない。

ギャップが2営業日以上開いたときの追いつき（§11 のステップ2）とは別のきっかけ。混同しない。

### なぜ本物の照合が必要か（§11 との関係）

`update_snapshot` からの転記（§11）だけで確定足を済ませ続けると、一度も取得先の確定履歴（`fetch_daily_bars`）と照合しないまま進んでしまう。それを防ぐため、`review_complete_date` から `review_lookback_days` × `review_trigger_multiplier` 日以上経っていたら、転記を試みず `update_daily_bars` を呼ぶ（§11）。

### 例（`review_lookback_days = 30`、`review_trigger_multiplier = 2`。毎日使う人）

12月26日に開く。前回の本物の照合（`review_complete_date`）が10月27日だったとする。10月27日から60日経っているので、発動の基準日数（`review_lookback_days` × `review_trigger_multiplier` = 60日）に達している。reviewが発動するため転記は試みず、この日は `update_daily_bars` を呼び、始点（10月28日）〜終点（持つべき最新の確定営業日）を本物の `fetch_daily_bars` で取得する。成功したら `review_complete_date` を11月26日（今日の30日前）に書き換える。次にまた本物の照合が必要になるのは、11月26日から60日後（翌年1月25日）。

## 11. `DailyBarService` の呼び出し順（`quote_time` 比較方式）

サービスは `DailyBarService` ひとつ。新しいサービスは作らない。銘柄1つに対する判定・後処理は、次の順で行う。`update_daily_bars_for_watchlist` は、これまでどおり銘柄ごとに `update_daily_bars` を呼ぶ薄いラッパー。`update_snapshots_for_watchlist` は、`fetch_snapshot` の呼び出しだけ監視銘柄をまとめて1回にする（§6）。銘柄ごとの判定・後処理はどちらも銘柄ごとに行う（名前を維持するか、1本にまとめるかは実装時に決める）。

### 判定に使う値：`latest_snapshots.quote_time`

新しい列。取得先が返す、最後の約定・気配の時刻をそのまま保存する（Yahooなら `regularMarketTime`）。現地の日付・時刻は、使うときにその都度変換して取り出す（`latest_bar_date` と同じく、列としては別に持たない）。

カレンダー（`is_trading_day`）と `session_close_time` だけで「今日は確定足があるはず」と判定すると、カレンダー上は営業日だが実際は休場（国葬など）の日に、実際のデータと食い違う判定をしてしまう。値の正本は取得先（§1）という方針どおり、`quote_time` は取得先が実際に返した最後の約定の時刻なので、休場の日は前営業日のままになる。これを `latest_bar_date` と比べることで、カレンダーのずれに影響されずに判定できる。

### 呼び出し順（銘柄1つ）

0. `snapshot_locked_until` より前の銘柄は、`fetch_snapshot` のバッチから除外する（§6）
1. 残った銘柄で `fetch_snapshot`（§6）を呼ぶ
2. 次のどちらかに該当する銘柄は、`daily_bar_locked_until` に関わらず `update_daily_bars`（§5）を呼ぶ。始点は `review_complete_date` の翌日、終点は今日
   - `review_complete_date` から `review_lookback_days` × `review_trigger_multiplier` 日以上経っている（§10）
   - `latest_bar_date` と、1で取得した `quote_time` の日付との差が2営業日以上ある

   成功したら `review_complete_date` を「今日 − `review_lookback_days`」に書き換える。失敗したときの扱いは §5「失敗時の扱い」を参照（エラーの種類でデバイス側／配信元側に分かれる）
3. その時点の `latest_bar_date`（2を実施していれば実施後の値、していなければそのまま）と、1で取得した `quote_time` を比べる
   - 日付が同じ → 「もう確定足に反映されている」。`latest_snapshots` を削除する。ロックは下記「snapshotからの転記」の4・5と同じ値にする
   - `quote_time` の日付が `latest_bar_date` の1営業日先、かつ現地時刻が `session_close_time` 未満 → 「まだ場中」。転記せず、`snapshot_locked_until` を `market_boundary_points` の次の `time` に、`daily_bar_locked_until` を今日の `daily_bar_reflect_time` に設定する
   - `quote_time` の日付が `latest_bar_date` の1営業日先、かつ現地時刻が `session_close_time` 以上 → 「もう閉場」。下記「snapshotからの転記」を行う

### snapshotからの転記

1. そのsnapshotの `open` / `high` / `low` / `last_price`（→ `close`）/ `volume` を、そのまま `daily_bars` の1行として upsert する
2. `adj_open` / `adj_high` / `adj_low` / `adj_close` も、素の値をそのまま入れる（その日は基準日になるため、調整の比率は常に1。§3.5）
3. `latest_snapshots` からその銘柄を削除する
4. `snapshot_locked_until` を、その日付＋1営業日の `quote_rollover_time`（8:45）に設定する
5. `daily_bar_locked_until` を、その日付＋1営業日の `daily_bar_reflect_time`（20:30）に設定する

これは §5 の `update_daily_bars` が成功したときの後処理と同じ内容。`update_snapshot`からの転記は`fetch_daily_bars` を呼ばずに済ませられる、という違いだけ。

### なぜこの順にするか

- 気配値の取得は日足の取得より軽い（§6）。多くの日は、これだけで確定足が済み、`fetch_daily_bars` を一度も呼ばずに終えられる
- 「閉場している」の判定は、今の時計の時刻ではなく、`quote_time`（取得できたsnapshotの対象セッションが実際にいつのものか）で行う。国葬のような日でも `quote_time` は前営業日のままなので、誤って新しい日付の足として扱わない
- `daily_bar_locked_until` を `session_close_time` ではなく `daily_bar_reflect_time`（20:30）にしているのは、取得先で日足が実際に確定するのがこの時刻頃のため（§2の調査メモ）。それより前にロックを解いても、fetchが無駄になるだけ
- 転記を試みる前に、必ずステップ2（レビュー・ギャップ判定）を行う。該当する場合は転記を試みず `update_daily_bars` を呼ぶ。転記しても直後の本物のfetchで同じ日付が上書きされるだけで無駄になるため


## 12. 既存の `DailyBarService` との接続（`01_Data_Layer.md` への落とし込み）

`01_Data_Layer.md` にある今のスキップは、おおむね次。

- `daily_bars` の最新 `trade_date` と、持つべき最新の確定営業日を比べる  
- 揃っていれば `update_daily_bars` は取りに行かない。足りなければ不足分だけ取る  
- きっかけはユーザ操作（起動、プレイリスト、デッキ、個別チャート、価格更新ボタン）  
- 定時の強制一括取得は作らない  
- 気配（snapshot）は `latest_snapshots.updated_at` で **30分に1回まで**

今回決めたことは、次を足す（または置き換える）こと。

- 新しい列 `latest_snapshots.quote_time`：取得先が返す最後の約定・気配の時刻。現地の日付・時刻は使うときに都度変換して取り出す（列としては別に持たない。§11）
- `latest_bar_date`・`last_answered_at`・`last_attempted_at`、`symbol_fetch_status` の列（§3 の表）
- `update_daily_bars` は1つの関数（§5）。始点は `review_complete_date` の翌日の1本だけ。終点は「今日」まで（§11）
- `DailyBarService` は銘柄ごとに、`fetch_snapshot`（ロック中の銘柄は除外）→ レビュー期限またはギャップ2営業日以上なら `update_daily_bars` → `latest_bar_date` とsnapshotの日付・`quote_time` を比べて「反映済み／転記／場中で待機」を判定する（§11）
- `update_snapshot`（§6）。確定日足と snapshot は別 API・別保存先（§3.5）
- `fetch_snapshot` は複数銘柄をまとめて受け取れる形にする（`symbol_ids: list`）。監視銘柄はまとめて1回、個別チャートは1銘柄だけで呼ぶ（§6）
- 確定足取得成功後（本物の取得・snapshot転記のどちらでも）: `latest_snapshots` 削除、`snapshot_locked_until`（翌営業日の `quote_rollover_time`。8:45）、`daily_bar_locked_until`（翌営業日の `daily_bar_reflect_time`。20:30）（§3.5・§11）
- `update_daily_bars` / `update_snapshot` とも、境界点（`market_boundary_points`。§2）の時刻でロック解除。`last_attempted_at` / `updated_at` からの相対時間では判定しない
- snapshotの転記で済まなかった銘柄は `fetch_daily_bars` で確定足を取りに行ける（§11）
- 途中で1日分だけ欠けても、専用の穴埋め処理は持たない。`review_lookback_days`・`review_trigger_multiplier` ごとの定期照合（§10）が期間ごと取得するときに、まとめて直る
- `review_lookback_days`・`review_trigger_multiplier` ごとの定期照合、`review_complete_date`（§10）
気配と確定日足の境界は、それぞれ別の境界点（`market_boundary_points`の行）で持つ。混ぜない。確定日足の `last_attempted_at` は、連打防止には使わない。ログ・観測用（§3）。

失敗時の段階的リトライ（一括→失敗分だけ個別→もう一度）はプロトタイプの参考。今回の本文では、空／通信エラーの分けまで合意。再試行の間隔・回数はまだ未固定（§5）。設計書に落とすとき、既存の「同じ時間枠では1回」と矛盾させない。

更新のきっかけは今どおりユーザ操作。定期照合（§10）も、専用の別バッチ・別サービスは作らず、起動やプレイリストを開いたときの `update_daily_bars_for_watchlist` に自然に乗る。ユーザーがアプリを開く日が人ごとに違うので、自然にずれる。
